# CLAUDE.md

## Project title

Построение метаграфового представления русскоязычного текста

---

## 1. Project overview

Этот проект посвящён построению метаграфового представления русскоязычного текста как формальной иерархической модели, способной отражать:

- синтаксическую структуру текста;
- рекурсивную вложенность конструкций;
- агрегацию фрагментов в более абстрактные единицы;
- переход от плоского семантического графа к многоуровневой модели знаний.

Проект является исследовательским. Главный приоритет — не максимальное количество функций, а:

- чистая и понятная архитектура;
- воспроизводимость преобразований;
- объяснимость каждого этапа;
- аккуратное развитие модели без скрытой магии;
- код, пригодный и для локальной разработки, и для дальнейшего масштабирования.

В этом проекте метаграф не рассматривается как декоративное представление поверх графа. Метаграф является самостоятельной моделью, в которой:

- вершины представляют базовые сущности;
- рёбра представляют отношения;
- метавершины представляют агрегированные фрагменты графа;
- метарёбра представляют реальные объекты модели, описывающие связи и/или процессы между агрегированными фрагментами.

## 2. MVP scope

Текущий pipeline разделён на две фазы:

```
Phase 1 (run_phase1) — тяжёлая, кэшируемая:
  raw text → normalize → sentences → parse (UD) → clauses (typed)
    → semantic graph → [anaphora resolution] → [NP collapse]

Phase 2 (run_phase2) — лёгкая, мгновенно перезапускаемая:
  semantic graph → metagraph L1 (clause metanodes + shared_entity)
    → metagraph L2 (paragraphs + entity_clusters + entity_centric
                    + predicate_class_clusters + topic_overlap)
```

Стадии в квадратных скобках — опциональные, управляются конфигурацией.
`run()` сохраняет старую сигнатуру и вызывает обе фазы — CLI и тесты
работают без изменений. UI кэширует `Phase1Result` в `session_state` по
ключу `sha256(text)[:16] + config.phase1_hash()` и перезапускает только
Phase 2 при смене настроек агрегации.

Что реализовано:

1. приём входного русскоязычного текста;
2. нормализация текста;
3. разбиение текста на предложения с paragraph_index;
4. морфо-синтаксический разбор: natasha **или** цепочка `razdel → TreeTagger → MaltParser`. TreeTagger даёт lemma + UPOS + feats через MSD-Russian tagset (Sharoff & Nivre), MaltParser — head + deprel; маппер `MsdTagMapper` переводит позиционные MSD-коды в UD-feats. Опционально — параллельно через `ProcessPoolExecutor` (`morphsyntax.workers`, `morphsyntax.parallel_threshold`);
5. выделение типизированных клауз (main, coord, compl, xcompl, adverbial, relative, participial);
6. построение ориентированного семантического графа по UD-ролям;
7. опциональное разрешение анафоры (`anaphora_resolution_v1`, замена-в-узле): личные / притяжательные 3-го лица / возвратные местоимения → антецедент с hard constraints по Gender/Number/Animacy и упрощённым Lappin–Leass salience-скорингом;
8. опциональная свёртка именных групп (NP collapse);
9. многоуровневая агрегация: L1 (clause metanodes, shared_entity metaedges), L2 (paragraph metanodes, entity_cluster — connected components, entity_centric — per-lemma метавершины, predicate_class_cluster, topic_overlap metaedges);
10. сохранение промежуточных артефактов (JSON, JSONL, YAML);
11. профилирование (wall time + peak memory на стадию);
12. audit trail с UTC-timestamps;
13. визуализация: pyvis HTML, GraphViz DOT, Cytoscape.js с compound nodes, toggle-фильтрами уровней и типов рёбер, объединением параллельных shared_entity;
14. Streamlit веб-интерфейс: двухсекционный sidebar (Phase 1 / Phase 2 — мгновенно), пресеты агрегации, авто-упрощение визуализации больших графов до L2-only, авто-определение кодировки загружаемых файлов;
15. CLI-команды `process` и `batch`.

Что не входит в текущий scope:

- графовая аналитика (центральности, community detection);
- поиск новых концепций;
- генерация научных выводов поверх корпуса;
- крупномасштабная автоматическая аналитика поверх метаграфа;
- LLM-ориентированные методы обработки.

Не добавляй такие функции в проект до тех пор, пока не будет явно поставлена отдельная задача.

## 3. Research constraints

Проект строится как объяснимая и в основном rule-based система обработки текста.

### Базовые ограничения

- Основной pipeline должен оставаться детерминированным и объяснимым.
- Основные преобразования должны быть выражены через правила, шаблоны, явные процедуры, морфологический анализ и структурные эвристики.
- Нельзя строить ядро системы вокруг нейросетей или LLM.
- Нельзя заменять явные правила "скрытым смысловым выводом" модели.

### Что разрешено

- классические алгоритмы NLP;
- морфологический анализ;
- синтаксические парсеры;
- OCR как предварительный этап извлечения текста;
- классические и вспомогательные ML-методы, если они не становятся обязательным ядром pipeline;
- вспомогательные обученные инструменты для MVP и тестирования.

### Что запрещено

- LLM как основной парсер текста;
- генерация графа или метаграфа "по смыслу" black-box моделью;
- зависимость всей архитектуры от нейросетевой модели;
- проектирование логики так, будто объяснение результата не требуется.

## 4. Linguistic modeling assumptions

### 4.1. Clause as the first metavertex

Клауза является базовой единицей агрегации и естественным кандидатом на роль метавершины первого уровня.

В рамках проекта клауза понимается как часть сложного предложения, имеющая предикативный центр.

Практически это означает:

- корнем клаузы обычно является предикат;
- предикат, как правило, выражен глаголом;
- предикат организует связи между субъектом, объектом, обстоятельствами и зависимыми элементами;
- клауза рассматривается как локально связный фрагмент смысла, который может быть сжат в метавершину.

Каждая клауза имеет лингвистический тип (`clause_type`), определяемый по
UD-deprel предиката: `main`, `coord`, `compl`, `xcompl`, `adverbial`,
`relative`, `participial`, `other`. Тип прокидывается в `MetaNode.type`
как `clause:{clause_type}`.

При работе над кодом всегда исходи из того, что:

- клауза — не просто участок текста;
- клауза — структурная единица семантического графа;
- клауза — первый уровень абстракции для построения метаграфа.

### 4.2. Semantic graph assumptions

Семантический граф в MVP — ориентированный.

Основные принципы:

- узлы представляют именные концепты, сущности или значимые смысловые единицы;
- рёбра представляют отношения, прежде всего глагольные или предложные;
- предикат играет роль структурного центра клаузы;
- граф должен быть пригоден для дальнейшей агрегации, а не только для локального синтаксического анализа.

### 4.3. Metagraph assumptions

Метаграф строится как результат "сжатия" или "сквизинга" исходного графа.

Под "сквизингом" понимается переход от плоских сырых вершин и рёбер к более абстрактным метаэлементам через правила агрегации.

Агрегация должна:

- быть объяснимой;
- быть трассируемой;
- не разрушать связь с исходным текстом;
- оставлять журнал того, какие элементы были агрегированы и по какому правилу.

## 4.4. Hierarchical dendrogram-like structure

Метаграф в данном проекте мыслится как многоуровневая иерархическая структура, строящаяся по принципу дендрограммы.

Это означает, что переход от семантического графа к метаграфу не является одношаговым. Вместо этого выполняется последовательность раундов агрегации, в ходе которых более простые элементы объединяются в более абстрактные.

Базовый уровень включает:

- именные группы, концепты и другие базовые смысловые единицы;
- отношения между ними;
- локальные графовые фрагменты, соответствующие отдельным предикативным структурам.

На следующих уровнях применяется общее правило агрегации:

- совокупность вершин и связей может быть объявлена одной метавершиной;
- такая метавершина становится новым объектом следующего уровня;
- далее она может участвовать в новых актах агрегации вместе с другими вершинами, метавершинами, рёбрами и метарёбрами.

Простейший пример: две вершины и связывающее их ребро могут рассматриваться как единый фрагмент и быть сжаты в метавершину. Аналогично более крупные подграфы, включая клаузы и повторяющиеся структурные паттерны, могут подниматься на следующий уровень абстракции.

Этот процесс является рекурсивным. Он повторяется до тех пор, пока:

- не перестают срабатывать правила агрегации;
- не достигнут заданный уровень абстракции;
- или не выполнены критерии остановки, определённые конфигурацией.

Такая организация важна по двум причинам:

1. Она позволяет представить текст как многоуровневую систему знаний, а не как плоский граф.
2. Она упрощает сравнение крупных блоков знаний на верхних уровнях иерархии, где подобие и структурный изоморфизм могут оцениваться между уже агрегированными фрагментами, а не только между исходными низкоуровневыми элементами.

## 5. Aggregation strategies

В проекте агрегация понимается как центральный механизм перехода от семантического графа к метаграфу.

На текущем этапе рассматриваются три базовые стратегии.

### 5.1. Linguistic aggregation

Агрегация на основе лингвистических единиц.

Примеры:

- клауза как метавершина;
- агрегация по типу предиката;
- агрегация по таксономии предикатов;
- агрегация по устойчивым синтаксическим структурам.

Это основная стратегия. Реализованные правила:

- `clause_as_metanode_v0` — клауза → L1-метавершина;
- `shared_entity_by_lemma_v0` — общие леммы → L1-метарёбра;
- `paragraph_clauses_v0` — параграф → L2-метавершина;
- `entity_cluster_v0` — connected components по shared_entity → L2-метавершины-«темы» (бывший `coref_cluster_v0`, переименован чтобы не путать с настоящей кореференцией). Из-за транзитивного замыкания union-find часто сливает большую часть текста в один компонент;
- `entity_centric_v0` — по одной L2-метавершине на каждую значимую лемму, содержащую все L1-клаузы, где эта лемма упоминается. Альтернатива union-find: не «темы как компоненты», а «темы как сущности». Одна L1 может входить в несколько entity-метавершин (холархия). PROPN-леммы при `propn_always=true` включаются при freq ≥ 1 (имена собственные всегда значимы);
- `predicate_class_cluster_v0` — кластеры клауз по семантическим классам предикатов из словаря `configs/predicate_classes.yaml` (motion / communication / cognition / …) → L2-метавершины;
- `topic_overlap_v0` — пересечение L1-фрагментов → L2-метарёбра;
- `anaphora_resolution_v1` — замена-в-узле для личных, притяжательных
  3-го лица и возвратных местоимений (он/она/оно/они, его/её/их с
  Poss=Yes, себя/свой). PRON-узел остаётся в графе: `lemma`/`upos`/`label`
  обновляются от антецедента, `original_lemma` / `original_upos` /
  `antecedent_node_id` сохраняют исходные значения и связь с
  антецедентом (CLAUDE.md §9.4 «no silent collapse»). Топология рёбер
  не меняется — связность возникает через `shared_entity_by_lemma_v0`.
  Hard constraints — Gender / Number / Animacy. Личные и притяжательные
  ранжируются упрощённым Lappin–Leass-скорингом (subj / obj / obl /
  propn / recency / thematic / repeat_mention); возвратные берут
  subject текущей клаузы. Запускается до агрегации, управляется
  конфигом `anaphora.enabled`, `anaphora.pronoun_types`,
  `anaphora.salience_weights`.

### 5.2. Structural aggregation

Агрегация на основе повторяющихся конфигураций графа.

Примеры:

- объединение повторяющихся подграфов;
- выделение типовых шаблонов;
- агрегация по структурному изоморфизму;
- сжатие одинаковых или почти одинаковых кусочков графа в единые метавершины.

Реализованный элемент: `np_collapse_v1` — свёртка именных групп. Для
каждого NOUN/PROPN-узла рекурсивно собирает UD-subtree модификаторов
напрямую из `ParsedSentence` через `Node.token_id_in_sent` (а не через
lookup-по-лемме среди узлов графа). Default `include_deprels`: `amod`,
`det`, `nummod`, `appos`, `flat`, `flat:name`, `nmod:poss`. `nmod` без
`:poss` намеренно НЕ сворачивается — он остаётся отдельным узлом + ребром
через `_expand_nmod` («анализ клауз» — 2 связанные сущности, а не одна).
Составная лемма формируется в порядке `Token.id_in_sent`, что даёт
правильный порядок и для левых amod («молодой исследователь»), и для
правых appos («исследователь иван»). Топология графа не меняется —
обновляются только лемма/surface головы и поля `original_lemma`/
`original_upos` (CLAUDE.md §9.4 «no silent collapse»). Запускается
после построения графа, до агрегации. Управляется конфигами
`aggregation.np_collapse_enabled` и `aggregation.np_collapse_deprels`.

Полноценная структурная агрегация (изоморфизм подграфов, шаблоны) — задача
дальнейшего развития.

### 5.3. Semantic aggregation

Агрегация по семантической близости.

Примеры:

- группировка вершин по косинусному сходству;
- объединение элементов по близости в векторном пространстве;
- вспомогательная семантическая группировка при исследовательских экспериментах.


### 5.4. General aggregation rules

Любая стратегия агрегации должна соблюдать следующие правила:

- результат агрегации должен быть объясним;
- агрегация должна сохранять provenance;
- агрегированные элементы должны оставаться связанными с исходными элементами;
- никакие элементы нельзя silently удалять без фиксации;
- новые метаэлементы должны иметь явный тип и происхождение;
- агрегация должна быть воспроизводимой при повторном запуске на тех же входных данных и конфигурации.

### 5.5. Multi-round aggregation

Агрегация в проекте должна рассматриваться как многораундовый процесс.

Это означает, что:

- сначала строится базовый уровень из исходных вершин и рёбер;
- затем выделяются локальные агрегаты;
- затем агрегаты предыдущего уровня могут становиться элементами следующего уровня;
- процесс повторяется рекурсивно.

Иными словами, агрегация работает не только "снизу вверх", но и как механизм построения иерархии уровней абстракции.

При проектировании алгоритмов агрегации необходимо учитывать, что:

- результат одного раунда становится входом следующего;
- на верхних уровнях сравнение структур может быть проще и устойчивее;
- критерии подобия, изоморфизма и структурного соответствия могут зависеть от уровня иерархии.

## 6. OCR policy

OCR допускается только как предварительный этап извлечения текста из неструктурированных источников:

- сканов;
- изображений;
- PDF без корректного текстового слоя.

OCR не считается частью семантического анализа и не должен смешиваться с логикой построения графа и метаграфа.

Если используется OCR, pipeline должен выглядеть так:

`image/pdf -> OCR -> text normalization -> sentence splitting -> clause extraction -> graph -> metagraph`

Правила:

- ошибки OCR должны рассматриваться отдельно от ошибок графовой логики;
- этап OCR должен быть изолирован;
- после OCR должна быть стадия очистки и нормализации текста;
- код OCR не должен проникать в модули, отвечающие за семантический граф или метаграф.

## 7. Architecture principles

При работе над проектом придерживайся следующих принципов.

### 7.1. Separation of concerns

Не смешивай в одном модуле:

- лингвистический разбор;
- графовую модель;
- агрегацию;
- сериализацию;
- отладочный вывод;
- CLI-логику.

Каждый слой должен решать свою задачу.

### 7.2. Explicit model over ad hoc structures

Предпочитай явные типы и модели данных случайным словарям и разрозненным tuple-структурам.

Хорошо:

- dataclass;
- pydantic models;
- отдельные типы для `Node`, `Edge`, `MetaNode`, `MetaEdge`, `GraphFragment`, `Clause`.

Плохо:

- безымянные dict с непредсказуемой схемой;
- вложенные структуры без контракта;
- логика, завязанная на "магические" ключи.

### 7.3. Deterministic transformations

Преобразования должны быть максимально детерминированными.

Если правило срабатывает по порогу, шаблону или эвристике:

- это должно быть явно задано;
- это должно быть описано в конфиге или коде;
- это должно быть понятно из результата.

### 7.4. Explainability first

Каждое нетривиальное преобразование должно быть объяснимо.

Нужно уметь ответить на вопросы:

- из какого текста появился этот фрагмент;
- из какой клаузы он произошёл;
- из каких узлов и рёбер он собран;
- какое правило создало метавершину;
- почему образовалось данное метаребро.

### 7.5. Readability over cleverness

Предпочитай понятный код умным, но непрозрачным абстракциям.

Не сокращай архитектуру ценой потери объяснимости.

### 7.6. Soft research style

Этот репозиторий ведётся в мягком исследовательском стиле.

Это означает:

- не превращай кодовую базу в жёстко зарегламентированный enterprise-проект;
- не вводи лишние слои абстракции без пользы;
- не делай тяжёлую инфраструктуру раньше времени;
- но сохраняй аккуратность, читаемость и ясность решений.

## 8. Working rules for Claude Code

При внесении изменений в проект:

1. Сначала пойми текущую архитектуру и уже существующие инварианты.
2. Не переписывай крупные модули без необходимости.
3. Не расширяй scope проекта без явного запроса.
4. Не подменяй исследовательскую модель "более удобной" плоской структурой.
5. Не превращай метавершины в простые теги или группы без внутренней структуры.
6. Не своди метарёбра к обычным рёбрам с флагом без серьёзного основания.
7. При добавлении нового правила:
   - опиши его идею;
   - укажи ограничения;
   - зафиксируй ожидаемый вход и выход;
   - покажи, что именно агрегируется.
8. При любом существенном архитектурном изменении оставляй краткую запись, пригодную для диплома или статьи.
9. Сохраняй промежуточные артефакты, когда это помогает отладке.
10. Предпочитай маленькие проверяемые шаги крупным непрозрачным переделкам.

## 9. Core invariants

Следующие инварианты считаются важными.

### 9.1. Text traceability

Любой значимый элемент графа или метаграфа должен быть связан с исходным текстом.

Минимум желательно хранить:

- `document_id`
- `sentence_id`
- `clause_id`
- исходный текстовый span
- правило происхождения

### 9.2. Metavertex integrity

Каждая метавершина должна:

- иметь собственный идентификатор;
- иметь тип;
- содержать или ссылаться на вложенный фрагмент;
- иметь происхождение;
- быть отличимой от обычной вершины не только флагом, но и смысловой ролью в модели.

### 9.3. Metaedge integrity

Каждое метаребро должно:

- быть самостоятельным объектом модели;
- иметь собственный идентификатор;
- иметь явно заданные начало и конец;
- иметь тип или класс отношения/процесса;
- иметь provenance;
- не сводиться автоматически к обычному ребру.

### 9.4. No silent collapse

Агрегация не должна незаметно уничтожать структуру.

Если элементы были объединены, это должно быть отражено явно:

- в lineage;
- в журнале преобразования;
- в структуре метаграфа.

### 9.5. Stable identifiers within a run

Идентификаторы объектов должны быть стабильны внутри одного запуска pipeline.

### 9.6. Stage boundaries

Каждая стадия pipeline должна иметь понятный вход и выход.

Нельзя писать код, где:

- одна функция делает сразу OCR, разбор, построение графа и агрегацию;
- промежуточные данные невозможно получить отдельно;
- логика спрятана в побочных эффектах.

## 10. Provenance and audit trail

В проекте желательно вести происхождение элементов как объект первого класса.

Для каждого созданного элемента полезно хранить:

- из каких элементов он возник;
- по какому правилу был создан;
- на каком шаге pipeline появился;
- какой конфиг был использован;
- какие параметры повлияли на решение.

Для сложных преобразований желательно иметь explain-output в формате:

- что было на входе;
- какое правило применилось;
- что было создано;
- что было заменено или агрегировано;
- какие неопределённости остались.

## 11. Data and artifact policy

Пока окончательный формат хранения не зафиксирован, придерживайся следующих принципов.

### 11.1. Human-readable first

На ранней стадии проектирования отдавай приоритет форматам, удобным для просмотра и отладки.

Подходящие варианты:

- JSON
- JSONL
- YAML для конфигов
- CSV/Parquet для табличных представлений

### 11.2. Persist intermediate artifacts

Не держи весь pipeline только в памяти, если данные полезно сохранять между этапами.

Полезные артефакты:

- нормализованный текст;
- предложения;
- клаузы;
- semantic graph;
- metagraph;
- audit log;
- profiling summary.

### 11.3. Version serialization formats

Если меняется схема хранения, фиксируй версию формата.

### 11.4. Avoid monolithic binary blobs

Не сохраняй всю структуру проекта только в одном непрозрачном бинарном файле, если это мешает отладке и исследованию.

## 12. Suggested module boundaries

Это ориентир, а не жёсткий закон.

### 12.1. `parsers/`

Отвечает за:

- нормализацию текста;
- сегментацию на предложения (с paragraph_index);
- выделение типизированных клауз (стратегии `ud_subtree_clauses_v0`, `sentence_as_clause_v0`);
- адаптеры morphsyntax: `MorphSyntaxParser` Protocol, `natasha_adapter`, `maltparser_adapter` (класс `TreeTaggerMaltParser`: цепочка razdel → TreeTagger → MaltParser), вспомогательный `treetagger_adapter` (`TreeTaggerMorph` — subprocess-обёртка TreeTagger как морфо-провайдера) и `treetagger_tagmap` (`MsdTagMapper` — MSD-Russian → UD UPOS+feats, словарь в `configs/treetagger_tagsets/msd_ru.yaml`);
- разрешение анафоры (`anaphora.py`, правило `anaphora_resolution_v1`):
  rule-based замена-в-узле для личных, притяжательных 3-го лица и
  возвратных местоимений. Классификация по приоритету
  reflexive → possessive_3p → personal_3p, маршрутизация на
  `_find_clause_subject` (возвратные) или `_find_antecedent_by_search`
  (остальные) с упрощённым Lappin–Leass salience-скорингом.

### 12.2. `graph_builders/`

Отвечает за:

- создание узлов и рёбер по UD-ролям (`from_clause.py`, билдер `ud_roles_v0`);
- свёртку именных групп (`np_collapse.py`, правило `np_collapse_v1`: рекурсивный обход UD-subtree через `token_id_in_sent`, сортировка по token-id, поддержка amod/det/nummod/appos/flat/nmod:poss; nmod без `:poss` остаётся отдельным узлом через `_expand_nmod`).

### 12.3. `aggregators/`

Отвечает за:

- L1: `clause_as_metanode` (клауза → метавершина), `shared_entity_metaedges` (общие леммы → метарёбра);
- L2: `paragraph_metanodes` (параграф → метавершина), `entity_cluster_metanodes` (connected components по shared_entity), `entity_centric_metanodes` (по одной L2-метавершине на каждую значимую лемму; альтернатива union-find кластерам — даёт несколько per-entity групп вместо одной большой компоненты связности), `predicate_class_cluster` (кластеры клауз по классам предикатов), `topic_overlap_metaedges` (пересечение L1-фрагментов).

### 12.4. `transforms/`

Отвечает за:

- переход между стадиями;
- применение правил;
- rewrite logic;
- формирование нового представления.

### 12.5. `domain/`

Содержит ядро модели:

- `Document`, `Sentence`, `Clause` (с `clause_type`)
- `Node` (с `token_id_in_sent` — якорь к UD-feats; `original_lemma` /
  `original_upos` / `antecedent_node_id` — заполняются для PRON-узлов
  после `anaphora_resolution_v1`), `Edge`
- `MetaNode`, `MetaEdge`
- `GraphFragment`
- `SemanticGraph`, `Metagraph`
- `AnaphoraResolution` (запись о замене местоимения: `pronoun_type`,
  `resolution_strategy`, `salience_score`, `matched_features`)
- `Provenance`, `IdFactory`

### 12.6. `io/`

Отвечает за сериализацию артефактов (JSON, JSONL, YAML, profiling.json).

### 12.7. `provenance/`

Отвечает за lineage, audit trail (с UTC-timestamps) и explainability.

### 12.8. `profiling/`

Отвечает за `StageMetrics`, `PipelineMetrics`, контекстный менеджер `measure_stage` (wall time + peak memory через tracemalloc).

### 12.9. `viz/`

Отвечает за:

- интерактивный HTML через pyvis (`html_pyvis.py`);
- статический GraphViz DOT (`dot.py`);
- Cytoscape.js HTML с compound nodes, инспектором, toggle-фильтрами по уровням (L0/L1/L2) и типам рёбер (base/shared_entity/topic_overlap/contains), объединением параллельных shared_entity рёбер (`cytoscape_export.py`). Параметры `hidden_levels` / `hidden_etypes` позволяют рендерить только верхние уровни для больших графов.

### 12.10. `web/`

Streamlit веб-интерфейс (`app.py`):

- двухсекционный sidebar: «Анализ текста» (Phase 1, требует пересчёта) и «Агрегация» (Phase 2, мгновенно);
- пресеты агрегации (`presets.py`): `clauses_only` / `entities` / `paragraphs` / `predicates` / `full` / `custom` — каждый задаёт явный набор boolean-тоглов агрегации;
- кэширование `Phase1Result` в `st.session_state` по ключу `text_hash + config.phase1_hash()` — смена настроек Phase 2 не пересчитывает парсинг;
- авто-упрощение визуализации больших графов: при `total_elements > viz_limit` рендер не запускается автоматически, пользователь выбирает «Только L2 (быстро)» (`hidden_levels=[0,1]` + все рёбра скрыты) или «Полный вид (медленно)»;
- авто-определение кодировки загружаемых файлов: utf-8 / utf-8-sig / cp1251 / cp866 / koi8-r.

## 13. Configuration policy

Конфигурация должна быть вынесена из кода настолько, насколько это полезно.

В конфиг стоит выносить:

- правила сегментации;
- параметры агрегации;
- пороги сходства;
- включение/выключение отдельных стратегий;
- режимы запуска;
- пути к данным;
- уровень логирования.

Не хардкодь такие параметры без причины.

## 14. Cross-platform policy

Проект разрабатывается преимущественно на Windows, но должен по возможности оставаться совместимым с macOS и будущим Linux/HPC окружением.

Правила:

- используй `pathlib`;
- избегай жёстких путей;
- основной запуск должен быть через Python CLI, а не через bash-only сценарии;
- shell-скрипты допустимы как дополнительные утилиты, но не как единственный способ работы;
- не завязывай архитектуру на особенности одной ОС;
- код должен корректно работать с UTF-8 и русскоязычными текстами на всех целевых платформах.

## 15. Performance policy

Хотя производительность не является единственной целью MVP, архитектура не должна загонять проект в тупик перед масштабированием.

### 15.1. CPU-first design

Предпочитай проектирование под CPU-first pipeline.

### 15.2. GPU is optional

Не делай GPU обязательным требованием архитектуры.

### 15.3. Document-level parallelism

Для будущей пакетной обработки основная единица параллелизма — документ.
В рамках одного документа реализован дополнительный уровень параллелизма
по предложениям на стадии `parse`: `ProcessPoolExecutor` с
`initializer=_worker_init` загружает парсер один раз на воркер и
переиспользует его. Активируется при `morphsyntax.workers > 1` и
`len(sentences) >= morphsyntax.parallel_threshold` (default 16) — на
малых документах spawn-overhead превышает выигрыш.

### 15.4. Serialization between stages

Проектируй стадии так, чтобы между ними можно было сохранять результат на диск и продолжать позже.

### 15.5. Profile before optimizing

Не вводи сложные оптимизации без измерений.

### 15.6. Avoid memory-heavy nested objects at corpus scale

На раннем этапе допустимы удобные объектные структуры, но при проектировании думай о переходе к более компактным представлениям для больших корпусов.

## 16. Debugging policy

Отладка в этом проекте критически важна.

Каждая стадия должна по возможности уметь:

- работать на одном документе;
- сохранять промежуточный результат;
- выводить inspectable representation;
- показывать причину применения правила;
- показывать, где и почему произошла агрегация.

Для сложных случаев полезен debug mode, в котором сохраняется всё:

- вход;
- нормализованный текст;
- предложения;
- клаузы;
- граф;
- метаграф;
- журнал правил;
- профилирование.

## 17. Non-goals

Не делай без отдельного запроса:

- тяжёлую распределённую инфраструктуру;
- сложную систему прав доступа;
- универсальный NLP framework;
- полноценную аналитику сложных сетей поверх метаграфа (центральности, community detection);
- генерацию научных выводов через LLM;
- "умную" автокоррекцию архитектуры без явного запроса.

## 18. Research writing and development journal

Проект должен по возможности сопровождаться текстовой фиксацией процесса разработки.

Цель:

- накапливать материал для диплома;
- накапливать материал для статей;
- фиксировать архитектурные решения;
- не терять ход мыслей и результаты экспериментов.

При значимых изменениях полезно сохранять краткую запись в одном из двух форматов.

### 18.1. Lab note format

Краткая техническо-исследовательская запись:

- дата;
- задача;
- гипотеза;
- что изменено;
- результат;
- ограничения;
- следующий шаг.

### 18.2. Thesis paragraph format

Краткий академический фрагмент, пригодный для вставки в диплом или статью.

Примеры тем для фиксации:

- изменение правил выделения клауз;
- изменение модели метавершины;
- новая стратегия агрегации;
- обнаруженная ошибка в интерпретации предиката;
- отличие между структурной и лингвистической агрегацией;
- ограничение OCR;
- сравнение двух подходов к разбору.

Если изменение влияет на модель, правила агрегации, интерпретацию клауз или границы допустимых методов, желательно оставить такую запись.

## 20. Final guiding principle

Главный принцип проекта:

Строить объяснимое и воспроизводимое преобразование

`text -> clauses -> semantic graph -> metagraph`

так, чтобы:

- клауза выступала базовой метавершиной первого уровня;
- агрегация была явной и трассируемой;
- метавершины и метарёбра были полноценными объектами модели;
- архитектура оставалась чистой, расширяемой и пригодной для исследовательской работы.
